# Deploying Zaviroq Workforce OS to Vercel + Supabase

This guide covers deploying **Zaviroq Workforce OS** using:
- **Vercel** for the React/Vite frontend and Express serverless API (`/api/*`) + Vercel Cron
- **Supabase** for PostgreSQL (pooled PgBouncer connection) and private Storage (`chat-images`)

---

## 1. Create the Supabase Project

1. Sign in to [Supabase](https://supabase.com/) and click **New Project**.
2. Choose a region close to your team (e.g., **Mumbai `ap-south-1`** for `Asia/Kolkata`).
3. Save your database password securely.
4. Go to **Project Settings -> Database -> Connection string**:
   - Select **URI** and **Transaction pooler (port `6543`, PgBouncer)**.
   - Copy the string; it looks like:
     `postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres?pgbouncer=true`
5. Go to **Project Settings -> API** and copy:
   - **Project URL** (`SUPABASE_URL`)
   - **`service_role` secret key** (`SUPABASE_SERVICE_ROLE_KEY`) — **never expose this in client code**.

---

## 2. Run the Database Migration

1. In the Supabase Dashboard, open **SQL Editor -> New query**.
2. Copy the entire contents of [`supabase/migrations/001_init.sql`](supabase/migrations/001_init.sql) and click **Run**.
3. Verify that:
   - All 16 tables exist (`employees`, `attendance`, `activity_logs`, `tasks`, `leaves`, `leave_balances`, `salaries`, `payroll_locks`, `chat_messages`, `announcements`, `audit_logs`, `settings`, `holidays`, `notifications`, `sessions`, `rate_limits`).
   - **Row Level Security (RLS)** is enabled on every table with **no public policies** (only the server using `DATABASE_URL` / `service_role` accesses the DB; the browser never connects to Supabase directly).
   - The `audit_logs` immutability trigger (`trg_audit_logs_no_update`, `trg_audit_logs_no_delete`) is active.

---

## 3. Create the Private Storage Bucket

1. In Supabase Dashboard, go to **Storage -> New bucket**.
2. Name the bucket **`chat-images`**.
3. Keep **Public bucket** **OFF** (private).
4. All uploads go through `/api/chat` and are served via short-lived signed URLs generated by the server (`server/storage.js`).

---

## 4. Seed the First Admin (or Migrate Existing SQLite Data)

Run from your local machine against the Supabase `DATABASE_URL` before opening the app to users.

### Option A: Clean Start (Recommended)
Creates the first real Master Admin from environment variables with `must_change_pin = TRUE`:

```bash
# PowerShell example
$env:DATABASE_URL="postgresql://postgres.<ref>:<pass>@aws-0-<region>.pooler.supabase.com:6543/postgres?pgbouncer=true"
$env:ADMIN_CODE="ZAV-001"
$env:ADMIN_NAME="Your Admin Name"
$env:ADMIN_EMAIL="admin@yourcompany.com"
$env:ADMIN_PIN="849201"
npm run seed:reset:pg
```

### Option B: Migrate Existing Local SQLite Data
```bash
$env:DATABASE_URL="postgresql://..."
npm run migrate:pg

# If you have inline base64 or /uploads/* chat images:
$env:SUPABASE_URL="https://<ref>.supabase.co"
$env:SUPABASE_SERVICE_ROLE_KEY="eyJ..."
npm run migrate:chat-images
```

## 5. Deploy to Vercel

1. Push this repository to GitHub/GitLab/Bitbucket (never commit `.env` or real secrets).
2. In [Vercel](https://vercel.com/), click **Add New... -> Project** and import the repository.
3. Framework preset: **Vite** (Vercel will also pick up `vercel.json` automatically).
   - Build Command: `npm run build`
   - Output Directory: `dist`
4. Add **Environment Variables** in Vercel (**Settings -> Environment Variables** for Production):

| Variable | Example / Notes |
| --- | --- |
| `DATABASE_URL` | Supabase Transaction Pooler URI (`:6543`, `?pgbouncer=true`) |
| `SUPABASE_URL` | `https://<project-ref>.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase `service_role` key (server-only) |
| `SESSION_SECRET` | Random 64-char hex string (`openssl rand -hex 32`) |
| `CRON_SECRET` | Random 32+ char secret used by Vercel Cron |
| `CORS_ORIGIN` | Your Vercel production URL (e.g. `https://zaviroq.vercel.app`) |
| `NODE_ENV` | `production` |
| `COOKIE_SECURE` | `true` |
| `APP_TIMEZONE` | `Asia/Kolkata` |
| `DEMO_MODE` | `false` |
| `ADMIN_CODE` | First admin employee code (e.g. `ZAV-001`) |
| `ADMIN_NAME` | First admin display name |
| `ADMIN_EMAIL` | First admin email |

5. Click **Deploy**.

## 6. Verify Vercel Cron Jobs

`vercel.json` configures two daily cron schedules (compatible with **Vercel Hobby**):
- **`/api/cron/auto-clockout`** (`30 18 * * *` UTC = `00:00 IST`): Closes stale shifts, ends overdue breaks, and marks stale employees `Offline`.
  - *Tip for 15-minute intervals:* Vercel Hobby limits built-in crons to once per day. On **Vercel Pro**, change the schedule in `vercel.json` to `*/15 * * * *`, or on Hobby trigger `GET https://your-app.vercel.app/api/cron/auto-clockout` every 15 minutes from an external cron service (e.g. cron-job.org / GitHub Actions) with `Authorization: Bearer <CRON_SECRET>`.
- **`/api/cron/daily`** (`35 18 * * *` UTC = `00:05 IST`): Marks absent employees for the previous workday and sends digest notifications.

Vercel automatically sends `Authorization: Bearer <CRON_SECRET>` when `CRON_SECRET` is configured in Environment Variables.

Verify manually:
```bash
curl -H "Authorization: Bearer $CRON_SECRET" https://your-app.vercel.app/api/cron/auto-clockout
```

## 7. First Admin Login & Smoke Test

1. Visit `https://your-app.vercel.app/api/healthz` -> expect `200 OK` with `{"ok":true,"db":"postgres"}`.
2. Open `https://your-app.vercel.app`.
3. Sign in with `ADMIN_CODE` (or `ADMIN_EMAIL`) and `ADMIN_PIN`.
4. Confirm you are prompted to **change your temporary PIN** (`must_change_pin = TRUE`) and accept the **Tracking Consent** screen.
5. Clock in (in Chrome/Edge over HTTPS) and verify `IdleDetector` permission prompt appears and `tracking_mode` shows `"system"`.

---

## 8. Rollback Plan

1. **Application rollback (Vercel):**
   - In Vercel Dashboard -> **Deployments**, click the `...` menu on the previous healthy deployment and choose **Instant Rollback**.
2. **Database rollback (Supabase):**
   - Take a Supabase Point-in-Time / manual backup before running new migrations.
   - Because `audit_logs` is append-only and migrations are additive, rolling back application code does not require destructive DB resets. If a schema change must be reverted, apply a compensating forward migration rather than truncating tables.
